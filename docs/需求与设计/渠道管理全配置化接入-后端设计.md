## 1. 目标与范围

**目标**：实现"任意数量的 A（上游）或 C（下游）公司，仅通过【渠道管理】数据配置即可接入运行，后端引擎零代码改动、零发版"。

对 B 而言 A/C 皆为**外部数据源**，其入站数据格式（字段名、嵌套结构、类型、时间格式）各不相同。本设计为 B 提供统一的"**外部格式 → B 内部契约**"翻译层，并复用既有校验、落库与推送链路。

**范围（In scope）**
- 入站映射配置 `receive_mapping` 的数据模型与承载。
- 入站映射引擎 `InboundMapper`（表达式解析 + 转换器 + 原始留痕）。
- 收单 `store`、验证码提交 `verifySubmit` 两个入口的前置映射改造。
- 缓存与配置热更新联动。

**非目标（Out of scope，本轮）**
- 不改造出站推送引擎（`ForwardService` / `push_steps.request_mapping` 沿用既有出站映射）。
- 不重写 `ProductOrderRequest` / `product_orders` 既有的校验与数据模型。
- 回调方向（A→B 异步回执）收敛为可选阶段（见 §10）。

## 2. 术语

| 术语 | 含义 |
| --- | --- |
| 外部方 | 对 B 而言的任一外部公司；A=`supplier_a`，C=`channel_c` |
| B 参考模型 | B 内部统一的订单域抽象字段键，外部数据翻译后的目标语言 |
| `receive_mapping` | 渠道行上按"入口"分段的入站映射配置（JSON） |
| 入口 | 同一外部方的不同入站动作：`order`(收单)、`verify`(验证码提交)、可选 `callback`(异步回执) |
| `__raw__` | 透传标记：未映射的外部字段统一收纳进原始留痕字段 |

## 3. 总体架构

```
外部方调用 (store / verifySubmit)
   │ ① 签名鉴权   VerifyChannelSignature（pid → 行内 key/algorithm + 限流）
   │ ② 授权校验   verifyProductForForward（channel_products × products × business）
   ▼
外部原始 payload
   │ ③ InboundMapper.mapForReceive(payload, channel.receive_mapping.<入口>)
   ▼
B 参考模型字段（user_phone / bus_code / sku_code / order_time / ...）
   │ ④ 统一校验   ProductOrderRequest（映射后严格校验，复用不变）
   │ ⑤ 落库       product_orders / product_order_tests
   │    原始终端留痕 ext_json + forward_orders.source_data
   ▼
  ⑥ 既有业务链路（事件 / 转发 / 回调）复用
```

原则：**一切差异进渠道行**，运行侧只按 `pid` 读配置驱动；代码中不得出现公司名/字面量特例。

## 4. 数据模型

### 4.1 `third_channels.receive_mapping`（JSON 列）

新增 JSON 列（若一期不做回调并入，仅含 `order` / `verify` 两段）：

```json
{
  "order": {
    "user_phone": { "from": "phone" },
    "user_phone|alt": "mobile",
    "bus_code": "bizInfo.serviceCode",
    "order_no": { "from": "orderId" },
    "order_time": { "from": "time", "convert": "datetime", "format": "YYYYMMDDHHmmss" },
    "price": { "from": "data.price", "convert": "numeric" },
    "total_amount": { "from": "data.amount", "default": 0 },
    "quantity": { "from": "count", "default": 1 },
    "province_code": "data.province",
    "__raw__": true
  },
  "verify": {
    "mobile": { "from": "phone" },
    "linkId": "linkId",
    "smsCode": "sms_code",
    "bus_code": "bizInfo.serviceCode",
    "sku_code": "sku"
  }
}
```

**健壮性**：业界对嵌套字段名用 `.` 分隔（如 `bizInfo.serviceCode`）；若外部合法字段名本身含 `.`，需在配置层转义约定（见 §6.2）。

### 4.2 迁移与校验变更

| 位置 | 变更 |
| --- | --- |
| 迁移 | `third_channels` 加 `receive_mapping`（text/JSON），幂等，默认 NULL |
| `ThirdChannelRequest` | `receive_mapping => 'nullable|array'`，并对 `order/verify` 段做结构校验 |
| `ThirdChannelService::getFormattedDetail` | 返回 `receive_mapping`（供前端回显） |
| `ThirdChannels` | `$fillable`、`$casts(receive_mapping => array)`、`$auditInclude` 补 `receive_mapping` |

### 4.3 缓存与热更新

- `receive_mapping` 随渠道整体配置缓存（沿用 `ChannelConfigLoader` 的 pid 维度缓存，TTL 3600s）。
- 渠道更新后由 `ThirdChannelService::clearCacheAfterUpdate` exp 失效；**配置即生效，无需发版**。

## 5. B 参考模型字段权威清单（订单域）

对齐 `ProductOrderRequest`（新增）与 `product_orders` 列；后续新增字段需在此登记并同步校验规则。

| 参考键 | 类型 | 必填(收单) | 说明 |
| --- | --- | --- | --- |
| `pid` | string | 是 | 渠道 PID（通常由鉴权/头注入，非外部字段映射） |
| `order_no` | string | 是 | 订单号（同一 pid 下唯一） |
| `user_phone` | string | 是 | 手机号（收单主键之一） |
| `bus_code` | string | 是 | 业务编码 |
| `sku_code` | string | 是 | 产品编码 |
| `price` | decimal | 是 | 单价 |
| `quantity` | int | 是 | 数量 |
| `total_amount` | decimal | 是 | 总金额 |
| `order_time` | datetime | 是 | 订购时间 |
| `user_nick` / `user_status` / `type` | 混合 | 否 | 会员/类型 |
| `province_code` / `city_code` | string | 否 | 区域 |
| `__raw__` | — | — | 透传未识别字段 |

## 6. `InboundMapper` 引擎设计

新增 `App\Services\ThirdChannel\InboundMapper`（对外提供 `mapForReceive(array $payload, array $mapping): array`）。

### 6.1 取值表达式（映射值的左侧=内部键，右侧=来源表达式）

| 形式 | 示例 | 说明 |
| --- | --- | --- |
| `string` 字符串 | `"mobile"` | 键名直接取值（含嵌套 `data.a.b`），不存在则跳过 |
| `{from}` | `{"from":"orderId"}` | 显式来源路径，不存在且无默认 → 跳过 |
| `{from, default}` | `{"from":"count","default":1}` | 缺失时用默认值 |
| `{value}` | `{"value":"gxhjy004"}` | 固定值 |
| `a|b|c` | `"phone|mobile"` | 候选取值，取第一个存在的 |
| `ignore:true` | `{"from":"uid","ignore":true}` | 不参与校验，仅用于取数到返回结果供留痕 |
| `__raw__` | `true` | 透传开关：收集所有未显式映射的外部键 → 返回 `__raw__` |

### 6.2 取值优先级与转义

1. 规范化来源路径：剥离首尾空白；支持转义分段符 `\.` 表示字面点（避免与嵌套分隔冲突）。
2. 取值顺序：候选集按序尝试 → `from` → 直接字符串 → `value`；命中即止。
3. 未知键（未被映射、映射值为 `ignore`、或命中 `__raw__`）→ 归入 `__raw__` 子集。

### 6.3 转换器（`convert`+`format`，白名单实现，禁任意表达式求值）

| 转换器 | 入参 | 行为 |
| --- | --- | --- |
| `datetime` | `format` | 按 `format` 解析为 `Y-m-d H:i:s`（如 `YYYYMMDDHHmmss` / `timestamp`） |
| `numeric` | — | 数值化（去货币符号、千分位） |
| `int` / `bool` | — | 类型强转 |
| `enum` | `map` | 外部值→内部值映射（`{"A":1,"B":2}`），未命中取默认或报缺 |
| `concat` | `parts` | 多路径拼接（如区号+手机号） |
| `strip` | `chars` | 去除指定字符（如空格、`+86`） |

- 转换失败：若字段在参考模型为"必需"，按 §8 失败策略拒绝；否则忽略并记日志。
- `convert` 仅在存在源值时执行；值为空串视为未提供。

## 7. 入口改造（`ReceiverController`）

### 7.1 `store`（收单，入口 `order`）

```
1. 鉴权取 channel / isTestEnv（既有）
2. 取原始 payload raw = $request->all()
3. rawMap = InboundMapper.mapForReceive(raw, channel.receive_mapping.order ?? [])
4. merged = (外部若已提供内部字段名则保留) + rawMap          # 平滑迁移：既有直接字段协议继续可用
5. 以 merged 构建校验输入，走 ProductOrderRequest 严格校验    # 或显式 $request->replace(merged) 再 validated()
6. verifyProductForForward(channel, merged)（既有授权校验）
7. 生成 trace_id，派发 ProcessOrderJob 等既有流程
8. __raw__ 写入 ext_json；raw 写入 forward_orders.source_data（既有字段）
```

### 7.2 `verifySubmit`（入口 `verify`）

现有硬编码 `mobile/linkId/smsCode/bus_code/sku_code` 改为：

```
1. 取原始 payload raw
2. vMap = InboundMapper.mapForReceive(raw, channel.receive_mapping.verify ?? [])
3. 从 vMap 取 mobile/linkId/smsCode/bus_code/sku_code，缺失走原必填校验
4. 复用既有：pendingVerify 查找 / bus·sku 一致性 / 次数限流 / 并发锁 / executeStep(1) / 状态机
```

> 保持既有失败语义（400/404/409/429/502）不变，避免破坏已对接方。

### 7.3 平滑迁移与回退

- 渠道未配置 `receive_mapping` → 映射为空映射，`mapForReceive` 原样返回（回落到既有"内部字段名协议"），**不破坏存量渠道**。
- `verifySubmit` 映射后仍缺关键字段时，报错信息同时给出"外部路径提示"便于排查。

## 8. 失败与审计策略

| 场景 | 策略 |
| --- | --- |
| 必需字段翻译后缺失 | 422，报内部参考键 + 来源外部路径 |
| 字段存在但格式非法 | 走既有 `ProductOrderRequest` 格式规则拒绝 |
| 转换器失败 | 日志记录；可选字段忽略，必需字段拒绝 |
| 透传/归一化 | 每次翻译保留原始 payload（source_data / ext_json）供稽核 |

## 9. 配置驱动与接入流程（后端视角）

新增外部方只需配置渠道行，后端无改动：

1. 建渠道：`ThirdChannelController::store`（name/pid/key/role/organization_id/status）。
2. 配产品授权：`syncProducts`（channel_products ↔ product）。
3. 配入站映射：`receive_mapping`（order/verify 段）。
4. 出站对接（若需要 B→外面）：沿用 `push_base_url` + `push_steps.request_mapping`（既有）。
5. 联调：测试环境（status=2）跑通 getCode→verifySubmit。

---

## 10. 回调方向收敛（可选阶段 C）

- 将 A→B 异步回执的 `callback_config.field_mapping` 并入 `receive_mapping`（新增 `callback` 段），由 `InboundMapper.mapForReceive` 取代 `ProvinceOrderInterpreter::applyFieldMapping` 的专属映射。
- 目的：全入站方向统一单一引擎，减少两套映射语义与维护成本。
- 本期**默认不落地**，作为可选后续。

---

## 11. 验收标准

1. 构造一个字段名/嵌套/时间格式均与内部不一致的外部方，仅配置 `receive_mapping` 后：
   - `store` 收单成功落库且 `ext_json` 保留原始 payload；
   - `verifySubmit` 验证码提交成功，`forward_status` 状态机正确。
2. 未配置 `receive_mapping` 的存量渠道行为与改造前完全一致（回归）。
3. 转换器（时间/数值/枚举）按预期归一化，缺失/非法按 §8 处理。
4. 新增渠道全程经 API 完成，后端无任何代码提交（验证 config-driven）。
