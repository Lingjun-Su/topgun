## 1. 目标与范围

**目标**：渠道管理页面成为"接入任意 A/C 公司的唯一总控台"。运营/实施人员**只需在页面上填写该渠道的通讯、入站映射、出站推送与产品授权**即可让一个新公司跑通，**无需改动任何前端代码**。

**范围（In scope）**
- 在新建/编辑渠道弹窗的【接收配置】Tab 内新增 `receive_mapping`（入站映射）可视化编辑器。
- 以入口分段管理 `order` / `verify` 两段映射。
- 保存/回显与后端 `receive_mapping` JSON 契约对齐。
- 与既有【产品配置】【推送配置】共同构成"一个渠道一个接入档案"。

**非目标（Out of scope，本期）**
- 不重做既有推送配置、多步骤推送、签名等已存在编辑器。
- 不改后端入站引擎（由后端设计文档承载）。
- 回调段（`callback`）编辑器默认不展示（后端未并入时）。

## 3. `receive_mapping` 数据契约（与后端一致）

```json
{
  "order": {
    "user_phone": { "from": "phone" },
    "user_phone|alt": "mobile",
    "bus_code": "bizInfo.serviceCode",
    "order_time": { "from": "time", "convert": "datetime", "format": "YYYYMMDDHHmmss" },
    "price": { "from": "data.price", "convert": "numeric" },
    "quantity": { "from": "count", "default": 1 },
    "__raw__": true
  },
  "verify": {
    "mobile": { "from": "phone" },
    "linkId": "linkId",
    "smsCode": "sms_code"
  }
}
```

- 映射键=内部参考字段（见后端文档 §5）；映射值=来源表达式（支持字符串键名 / `from` / `default` / `value` / `a|b` 候选 / `ignore`）。
- `__raw__`：布尔透传开关，开启后未映射的外部字段收纳进原始留痕。
- 未配置任一段 → 后端按默认内部字段协议处理（编辑回显为空；保存可留空）。

## 4. UI 结构与交互

### 4.1 入口分段器

- 本地状态 `receiveTab`：`order` / `verify`，切换时仅展示当前段映射。
- 分段标签：`收单 order`、`验证码 verify`。

### 4.2 映射表（每段一张）

| 列 | 控件 | 说明 |
| --- | --- | --- |
| 内部字段 | `q-input`（下拉含参考字段清单） | 目标参考键（如 `user_phone`/`bus_code`/`order_no`） |
| 来源/表达式 | `q-input` | 键名、嵌套 `a.b`、候选 `a\|b`、`value` 固定值等 |
| 能力 | 一行轻量控件 | 转换器下拉 + 参数 + 默认值 + 忽略开关 |
| 操作 | 删除行 | — |

每段底部：`+ 添加映射`、`启用 raw 透传（__raw__）`切换。

### 4.3 表达式/转换器编辑（能力行）

- 选中转换器时展开一行参数：
  - `datetime` → 格式下拉（`Y-m-d H:i:s` / `YYYYMMDDHHmmss` / `timestamp`）
  - `numeric` / `int` / `bool` → 无需参数
  - `enum` → 映射表（外值→内值，`q-input` 对）
  - `concat` → 多个来源输入
  - `strip` → 待去除字符
- 默认值：仅当配置 `default` 时显示输入框。
- 忽略开关：置真则该内部字段不参与必填校验。

> 样式复用 Quasar 既有 `q-input/q-select/q-list`；能力控件折叠于行内，降低视觉噪音。

### 4.4 交互流程

1. **新增/编辑加载**：`openDialog` 编辑时从 `channelApi.show` 取后端 `receive_mapping`，经 `normalizeJson` 后转可视化结构；无则空段。
2. **保存**：`saveChannel` 组装 `form.receive_mapping`（段 → 映射对象），随渠道表单提交；`store`/`update` 同路径。
3. **必填校验**：内部字段列留空时前端拦截并提示，防止提交脏配置。
4. **回显**：保存后重开弹窗，配置原样还原。

## 5. 前端状态与表单字段

- `form` 增加 `receive_mapping: null`；新增/编辑 `Object.assign` 中同步初始化/回填。
- 可视化中间态（不进 payload）：
  ```js
  const receiveMappingUI = {
    order: { rows: [{ internal, source, convert, convertParam, defaultValue, ignore }], raw: false },
    verify: { rows: [...], raw: false },
  }
  ```
- 提交时由 `rows → mapping` 转换（表达式结构化 JSON）；加载时反向 `mapping → rows`。
- 转换函数建议抽为 composable：`src/composables/useReceiveMapping.js`（`toModel` / `toUI` / 校验）。

## 7. 兼容性与回归

- 存量渠道 `receive_mapping` 为空 → 编辑器显示空，保存清空不影响后端默认协议。
- 不恢复此前已取消的【接收接口地址/自动转发/回调类型/订单状态映射】UI。
- 保存/列表/详情接口契约向后兼容（`receive_mapping` 为可空新增字段）。

---

## 8. 验收标准

1. 新建渠道：填写基本信息 + 产品授权 + `receive_mapping`（order/verify），保存成功并回显一致。
2. 用一份与内部字段名不同的模拟 payload，在前端配置映射后能命中预期内部字段（与后端联调验证翻译命中）。
3. 分段切换 order/verify 互不串扰；转换器参数折叠/展开、默认值、忽略开关行为正确。
4. 未配置 `receive_mapping` 的存量渠道编辑/保存不报错、不改动其他字段。
5. 页面零硬编码公司名；字段清单由参考字段下拉提供。
