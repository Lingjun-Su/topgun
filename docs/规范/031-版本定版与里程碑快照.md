# 031 · 版本定版与里程碑快照

适用范围：所有项目。定义"版本 / 定版"概念，以及定版后从 GitHub 上传到任务清理、阶段总结的完整动作；核心目的是以定版为 AI 上下文的**记忆检查点**，压缩过往、沉淀当前，降低记忆膨胀。

## 概念

- **版本**：一套通过测试、达到验收标准、可发布的代码状态组合——含代码、`doc/` 文档与规范副本，以 SemVer `主.次.补丁` 标识。
- **定版**：该版本经 PM 验收通过后**冻结**。定版后不再无版本号改动；任何后续改动一律归入下一版本。

## 定版触发

- **唯一触发：PM 验收通过**（架构师汇总交付后）。
- 架构师**不得自动定版**；验收通过即定版，按下方四步执行。

## 定版四步

### 1 · 升版本并更新变更日志

将当前版本号递增为 `v<主>.<次>.<补丁>`，在项目根 `CHANGELOG.md` 追加本版条目：范围、新增/修复/废弃、涉及规范与接口变更。

### 2 · 打 tag 并上传 GitHub

- 打 SemVer 标签：`v<主>.<次>.<补丁>`。
- 推送代码到发布分支；规范副本、接口契约、文档随代码一同纳入本次提交。
- 创建 **GitHub Release**，把里程碑快照作为发布包附件一并上传，形成完整版本交接包。
- GitHub 连接与托管信息登记于 `资源与凭证/`，由定版项目在验收通过后执行上传。

### 3 · 清理过往任务

- 将 `doc/协同/` 中已验收通过的任务单与对应回单**成对移入 `doc/协同/归档/`**（按本版本归档子目录组织）。
- 将各角色**工作日志一并封存**：`doc/工作日志/架构师.md`、`frontend/doc/工作日志/`、`backend/doc/工作日志/`、`test/doc/工作日志/` 移入 `doc/协同/归档/<版本>/工作日志/`（见 `033`）。封存后不再进入常规 AI 上下文，以压缩记忆。
- 未了结任务**不删除**，显式列为遗留项写入里程碑快照。
- 归档是压缩而非丢弃：完整历史在归档中保留，可追溯。

### 4 · 生成里程碑快照（记忆压缩点）

快照写入 `doc/里程碑/MILESTONE-<版本>.md`，**全量保留**，按版本累积。字段模板：

```
版本号 / 定版日期
本版功能范围（已验收项）
遗留问题 / 技术债
依赖与接口变更
规范变更（指向开发规范/ 版本）
资源变更（端口 / 凭证，见资源与凭证/）
下一步计划
给下一会话的上下文摘要
```

## AI 记忆管理

- 里程碑快照即**记忆检查点**：每个版本一份，后续会话以**最近一份快照**为启动上下文，需要时才惰性读取历史归档。
- 三条约束控制记忆膨胀：
  1. 定版前清理协同区（归档 + 快照），已了结的往返记录不再进入常规上下文。
  2. 快照的「上下文摘要」字段承载当前项目状态，作为后续 AI 的唯一启动上下文。
  3. 未完成事务（进行中任务、遗留问题）必须显式写进快照，避免定版后被遗忘。

## 与规则库的级联

若本次定版伴随全局规则变更，先回到 `开发规范/` 升版定稿并下发（见其变更日志），再在快照中记录本次规范变更，保持一致与可追溯。
