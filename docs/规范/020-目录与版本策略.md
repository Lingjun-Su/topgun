# 020 · 目录与版本策略

适用范围：所有项目的分支、提交与版本号约定。项目顶层目录骨架统一遵循 [`022-项目目录与文档规范`](./022-项目目录与文档规范.md)。

## 仓库布局

* 业务项目默认**独立仓库 + 独立部署**；被多方共用的能力（API 网关、共享库、设计令牌）独立成库，由 `资源与凭证/` 登记引用关系。

* 项目顶层统一为 `frontend/`（前端）、`backend/`（后端）、`doc/`（文档中心）等骨架，结构见 022；`backend/` 内部再按 001、`frontend/` 内部按 002、小程序按 004 组织。

## 分支模型

推荐 GitFlow 收敛版：

```
main（可发布）
 └─ develop（集成）
     ├─ feature/<工单号>--<slug>   # 功能分支，合并回 develop
     ├─ release/<x.y>              # 发布分支，倒回 main
     └─ hotfix/<工单号>--<slug>    # 紧急修复，回 main 并同步 develop
```

* `main`/`develop` 保持可运行；功能分支以工单号开头便于追溯。

* 单一小型项目可用 trunk-based（短生命周期分支直连主分支），需在 `项目表.md` 注明所选模型。

## 提交规范（Conventional Commits）

| 类型         | 适用     | 示例                           |
| ---------- | ------ | ---------------------------- |
| `feat`     | 新功能    | `feat(orders): 新增批量导出`       |
| `fix`      | 缺陷修复   | `fix(auth): 修正令牌过期判断`        |
| `refactor` | 重构不改行为 | `refactor(service): 抽取订单状态机` |
| `docs`     | 文档     | `docs: 补充分页约定`               |
| `chore`    | 杂项/依赖  | `chore: 升级依赖`                |
| `test`     | 测试     | `test(api): 覆盖分页边界`          |

## 版本号

* 遵循 **SemVer** `主.次.补丁`：主版本 = 破坏性变更（含接口不兼容），次版本 = 向后兼容新功能，补丁 = 兼容修复。

* 对外接口版本与主版本对齐，接口破坏性变更必须升主版本。
