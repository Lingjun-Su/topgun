# 022 · 项目目录与文档规范

适用范围：所有新项目按本规范的统一骨架初始化。本规范定义**项目顶层目录**与**项目必带文档**；各技术栈内部的具体结构分别遵从其对应规范（`001-Laravel后端规范` / `002-Quasar2前端规范` / `004-微信小程序规范`）。

## 项目统一骨架

```
<项目名>/             # 项目名 = 项目表.md 登记的名称/代号
  ├── frontend/       前端工程（Quasar2 见 002；小程序见 004）
  ├── backend/        后端工程（Laravel 见 001）
  ├── doc/            文档中心（结构见「文档中心 doc/」）
  ├── test/           测试员专属工作区（可选，收纳前后端产物、用例日志；见 032/033）
  ├── scripts/        脚本与本地工具（构建、联调、mock 数据，可选）
  ├── deploy/         部署与配置（可选，按项目需要）
  ├── README.md        项目简介（见「项目必带文档」）
  ├── CHANGELOG.md     版本与变更记录
  └── .env.example     环境变量样例（必提交，密钥不入库）
```

## 顶层目录职责

| 目录             | 职责                | 约束 / 内部结构                                             |
| -------------- | ----------------- | ----------------------------------------------------- |
| `frontend/`    | 前端工程              | Quasar2 遵 002；微信小程序以 `miniprogram/` 承载遵 004           |
| `backend/`     | 后端工程              | Laravel 遵 001：`app/`、`routes/`、`database/`、`tests/` 等 |
| `test/`（可选）  | 测试员专属工作区           | 同时收纳前端/后端投递产物（见 032），`test/doc/` 放工作日志；与 frontend/backend 源码隔离 |
| `doc/`         | 文档中心              | 结构见下，含规范围下发的规范副本                                      |
| `scripts/`（可选） | 构建、本地联调、mock 工具脚本 | 只做工具，不承载业务逻辑                                          |
| `deploy/`（可选）  | 部署配置、编排与 CI 片段    | 若使用则登记维护                                              |

## 文档中心 doc/ 结构

```
doc/
  ├── README.md         文档导航
  ├── 需求与设计/         需求说明、方案、原型说明
  ├── 协同/               Agent 协同通道：任务与反馈的文档交换区（见「Agent 协同通道」）
  ├── 接口文档/           接口契约说明（或引用后端生成的文档）
  ├── 数据库/            表结构说明与 ER 图
  ├── 里程碑/            各定版版本的里程碑快照（记忆检查点，见 031）
  ├── 会议与决策/         关键决策与技术评审记录
  └── 规范/              大管家下发的最新规则副本（只读，以开发规范/为准）
```

## Agent 协同通道（doc/协同/）

架构师、程序员、测试员之间**不直接对话**，一切信息交换都经由 `doc/协同/` 下的固定通道文档完成。
通道是端到端的唯一通信方式：派单、回执、测试结论都写成文档，靠读写通道完成信息流转，任何 Agent 不得用对话方式直接改动他人的任务或传递结果。
各角色可访问的目录边界与权限隔离见 `032-角色工作目录与访问边界`。

### 通道目录结构

```
doc/协同/
  ├── 任务单/               架构师 → 追溯主档（派单）
  │     └── 任务-<任务号>-<目标>-<vN>.md
  ├── 测试接收/             架构师 → 测试员（投递：工单副本/验收标准/需求/接口·库说明）
  ├── 测试回单/             测试员 → 架构师（测试结论）
  │     └── 测试-<任务号>.md
  ├── 测试工作日志/          测试日志归档副本（主档见 033：`test/doc/工作日志/`）
  └── 归档/                 验收通过后，成对移入（保留任务单 + 各回单 + 工作日志封存）
```

> 投递/回传落点按 `032-角色工作目录与访问边界`：架构师把任务单及资料投递到**各角色各自可见目录**（前端 `frontend/doc/`、后端 `backend/doc/`、测试 `doc/协同/测试接收/`）；**程序回单**由程序员写入各自业务目录 `doc/回单/`（不经 `doc/协同/`），测试回单仍经 `doc/协同/测试回单/`。

### 通道文档清单

| 文档   | 方向      | 必含字段                                                 | 说明                 |
| ---- | ------- | ---------------------------------------------------- | ------------------ |
| 任务单  | 架构师→执行者 | 任务号 · 指派对象 · 描述 · 模块位置 · 验收标准 · 测试要求 · 依赖 · **引用规范** · 状态 · 版本         | 架构师写入 `doc/协同/任务单/` 主档，并投递送达副本到执行者可见目录（见 032） |
| 程序回单 | 程序员→架构师 | 任务号 · 结果(`completed` / `needs_change`) · 完成说明 / 问题清单 | 落于各自业务目录 `doc/回单/`；程序员只做反馈，不改任务单 |
| 测试回单 | 测试员→架构师 | 任务号 · 已测范围 · 用例数 · 发现问题 · 结论(`pass` / `fail`)        | 依据任务单验收标准 + 边界用例测试 |
| 状态回写 | 开发岗（前后端程序员）→任务单 | 仅开发岗更新任务单内 `状态` 字段；测试员对任务单**只读**，不写状态（见 030/032） | 随进度推进，见下方状态机       |

### 状态下发与回执状态机

```
TO_DO ──认领──► DOING ──完成──► DONE（等待验收）
                │                 │ 测试 fail 或回单 needs_change
                └─────────◄───────┘
                架构师修改任务单并升版本 vN+1，重新下发
验收通过 ► DONE 回单/测试单 成对移入 归档/
```

* 认领：**开发岗（前后端程序员）**把任务单 `状态` 置为 `DOING`；测试员不认领、不写状态。

* 纯测试任务（无开发岗执行者）：由架构师在测试启动时将状态置为 `DOING`，测试回单产出后由架构师确认并置为 `DONE`。

* 反馈：程序员写 `程序回单`，结果置 `completed` 或 `needs_change`；测试员写 `测试回单`，结论置 `pass` 或 `fail`。

* 需修改：架构师只能在通道内**修改任务单并递增版本**后重新下发，不回滚、不口头改。

### 通信守则

1. 一切以 `doc/协同/` 内的文档为准，不直接对话、不口头传递需求或结果。
2. 程序员、测试员**不得修改任务单内容**；变更意见只能写进各自回单。
3. 架构师**不代写代码、不代做测试**；只依据回单与测试单判断如何修改与重派。
4. 每个回单必须能在通道内对上同名任务单（同任务号），保证成对约束、可追溯。

作业流即 `030-架构师职责与工作流` 的闭环：架构师派单 → 程序员写码回单 → 需要修改则架构师改单重派 → 测试员出结论 → 正确则汇总交 PM 验收。

## 项目必带文档清单

| 文档             | 位置        | 内容                    |
| -------------- | --------- | --------------------- |
| `README.md`    | 项目根       | 项目简介、技术栈、目录导航、本地启动步骤  |
| `CHANGELOG.md` | 项目根       | 版本与变更记录               |
| `.env.example` | 项目根       | 环境变量样例（必提交，密钥与真实值不入库） |
| `doc/规范/`      | 项目 doc/ 下 | 大管家下发的最新规则副本          |

## 规范副本（doc/规范/）

* 存放 `开发规范/` 的最新副本，由大管家在规则变更时同步推送（机制见 `开发规范/README.md`）。

* 项目内**只读**，不得在项目内直接修改；规则改动一律回到 `开发规范/` 定稿后再下发。

## 单一技术栈 / 小程序项目适配

* 微信小程序项目：`frontend/` 内放 `miniprogram/`，后端仍为 `backend/`；也可按需求在顶层直接用 `miniprogram/`。

* 只有单一技术栈（纯后端或纯前端或纯小程序）时，可省略不存在的空目录，但 `doc/` 与根文档必建。

* 目录名一律英文小写（frontend / backend / doc），中文含义见上表，避免跨平台路径与工具链编码问题。

## 立项初始化

新增项目建立子目录时按本骨架起底，完成 `021-项目注册` 的登记与规范下发，并建立 `doc/协同/` 下的四类交换目录（任务单 / 程序回单 / 测试回单 / 归档）。通道目录随项目一起初始化，作为 Agent 协作的固定基础设施。
