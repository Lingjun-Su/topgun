运营商 / 业务 / 渠道订单与合同管理后台。系统覆盖运营商与业务产品配置、第三方渠道订单接入与推送、数据中转与回调日志、产品订单全链路追踪与报表、组织架构（公司 / 部门 / 岗位 / 员工）以及框架合同与执行合同的审核流转。

本地启动

后端（backend/）

  1. 安装依赖：composer install
  2. 配置环境：复制 .env.example 为 .env，填写 SQL Server 连接（库名 topgun）并生成密钥 php artisan key:generate
  3. 初始化数据库：php artisan migrate --seed
  4. 启动服务：php artisan serve（默认 http://127.0.0.1:8000）
  5. 队列与定时任务：php artisan queue:listen --tries=1，php artisan schedule:work

前端（frontend/）

  1. 安装依赖：npm install
  2. 启动开发：npm run dev（Quasar 默认端口，开发代理 /api → http://127.0.0.1:8000）
  3. 生产构建：npm run build

  • 管理后台接口：/api/v1/**（Sanctum 令牌鉴权，见 doc/接口文档/）

000-通用规范

000 · 通用规范

适用范围：所有技术栈。以下原则作为各技术栈专属规则的基础。

命名即文档

  • 标识符自解释：读名即知其意，不靠注释补救含义。
  • 与领域用语一致：业务中的叫法在代码、接口、表里保持同一个词。

注释只写为什么

  • 不解释某段代码"做了什么"——那由命名与结构表达。
  • 只记录非显见的约束、取舍、历史原因或外部依赖的坑。

消灭魔法值

  • 字面量全部集中在常量/配置中管理。
  • 禁止在业务代码中散落裸数字与裸字符串。
  • 语义相同的值必须复用同一个常量源，不允许两处各自定义。

单一职责

  • 类、函数、组件、方法只做一件事，过长即拆分。
  • 每一层只负责自己的边界：HTTP 层不问业务，业务层不碰 HTTP 细节。

错误面向两端

  • 用户看到可读提示，日志留足上下文（含 trace_id）。
  • 禁止吞异常、禁止空 catch；处理不了就向上抛，不假装成功。

依赖与入口

  • 优先依赖注入与显式传参，减少对全局状态的隐式依赖。
  • 数字金额一律用精确十进制（分或 decimal），禁止浮点算钱。

代码风格基调

  • 缩进统一（后端/脚本 4 空格，前端 2 空格），与各栈对应规范一致。
  • 提交前保证本模块可运行、可构建，不留半成品。

001-Laravel后端规范

001 · Laravel 后端规范

适用范围：Laravel 后端项目。

代码风格

  • 遵循 PSR-1 / PSR-12，命名空间按 PSR-4 映射到 app/ 对应目录段。
  • 类名 UpperCamelCase、方法/变量 lowerCamelCase、常量 UPPER_SNAKE（详见 005）。
  • 优先依赖注入与容器解析，避免在业务代码里滥用门面与全局 helper。

分层职责

层目录职责约束
Controllerapp/Http/Controllers接 HTTP、调度 Service、组装响应保持"薄"，不写业务逻辑
Requestapp/Http/Requests参数校验与权限门面校验规则内聚进请求类
Serviceapp/Services业务编排与领域逻辑可复用，不依赖 HTTP 细节
Repositoryapp/Repositories数据存取封装按聚合划分，不写业务规则
Modelapp/ModelsEloquent 映射、关系、作用域声明 $fillable、关系与局部作用域
DTOapp/DTO跨层传输的不可变结构复杂入参用 DTO，避免数组满天飞
Traitsapp/Traits按标签复用能力仅放置无状态能力，不承载状态

数据与迁移

  • 结构变更走迁移，禁止直接改库；种子与工厂用于环境初始化与测试。
  • 模型统一声明 $fillable 而非 $guarded，避免意外批量赋值。
  • 业务表提供 created_at / updated_at，按需要扩展软删除与审计字段。

输入校验与响应

  • 外部入参一律经 Request 校验类处理，业务层不再重复信任输入。
  • 响应走统一返回结构（见 010 接口契约），业务层抛领域异常而非在 Controller 堆 try/catch。
  • 时间用 Carbon、以应用时区为基准，对外传输统一 ISO 8601。

关于存储过程

  • 业务逻辑留在 Service（PHP），存储过程仅限复杂事务或批量计算场景。
  • 使用存储过程必须在项目中登记目的，避免隐式数据逻辑失控。

002-Quasar2前端规范

002 · Quasar2 前端规范

适用范围：Quasar2 / Vue3 前端项目。

目录结构

src/
  ├── api/           # 接口请求统一封装层
  ├── stores/        # Pinia 状态
  ├── router/        # vue-router 配置与守卫
  ├── layouts/       # 布局组件
  ├── pages/         # 路由页面
  ├── components/    # 通用与业务组件
  ├── composables/   # 组合式函数 useXxx
  ├── utils/         # 纯函数与工具（含 constants/enums）
  └── assets/        # 样式、静态资源

组织与状态

  • 使用组合式 API + script setup，逻辑复用走 useXxx 组合式函数。
  • 跨组件共享的取数与状态统一由 Pinia 承载，不在组件内裸发请求。
  • 页面组件只做"编排与展示"，把可复用的交互拆成 components/，把可复用的逻辑拆成 composables/。

请求层

  • 所有后端请求集中在 api/ 封装 baseURL、鉴权头与统一拦截，页面不直接拼 URL（详见 010）。
  • 鉴权头统一走 Bearer Token，令牌由状态或缓存统一持有并注入拦截器。

命名与样式

  • 组件命名 UpperCamelCase，页面以业务语义命名。
  • 布尔变量用 is/has 前缀，事件回调与 props 语义封闭。
  • 样式可使用 BEM 或组件 scoped；主题令牌（颜色、间距、字号）集中定义供全站复用，不散落魔法色值。

枚举

  • 业务枚举值只在 src/utils/constants 映射展示，不做业务判断（详见 006）。

003-SQLServer数据层规范

003 · SQL Server 数据层规范

适用范围：SQL Server 数据层设计。

表与字段

  • 表名用复数业务语义（users、orders），字段用 snake_case。
  • 主键默认 bigint identity；业务确实需要自然键时单独在项目内约定并登记。
  • 每张事实表提供 created_at / updated_at；审计类字段（created_by / updated_by）按业务需要扩展。

类型选择

场景类型说明
文本（含中文）NVARCHAR不用 VARCHAR，避免中文编码隐患
时间datetime2精度精确，不用旧 datetime 混淆语义
金额decimal精确十进制，禁浮点存钱
布尔bit语义即布尔，不用 int 0/1
主键bigint identity默认主键形态

索引

  • 外键列必建索引，避免关联走全表扫描。
  • 高频查询按覆盖查询建索引（include 拉取所需列）。
  • 避免重复索引与冗余索引；索引变更随迁移管理、可回滚。

迁移与变更

  • 结构变更走迁移脚本管理，禁止手工改生产库。
  • 破坏性结构变更（删列、改类型）必须先在测试库演练，并在变更日志留痕。

存储过程

  • 仅限复杂事务或批量计算使用；普通业务查询走应用层（Laravel Service/Repository）。
  • 每个存储过程在项目中登记"用途"，便于审计与维护。

软删除与审计

  • 软删除用 deleted_at 列 + 应用层软删除机制，不物理删业务数据（归档策略另行约定）。

004-微信小程序规范

004 · 微信小程序规范

适用范围：微信小程序项目。小程序的接口调用与业务数据往往复用后端，需与后端规则（010 接口契约、006 枚举）保持一致。

目录结构

miniprogram/
  ├── app.js                 # 全局逻辑与全局变量
  ├── app.json               # 全局配置（页面、窗口、tabBar）
  ├── app.wxss               # 全局样式
  ├── pages/                 # 页面（每页一个目录：wxml/wxss/js/json）
  ├── components/            # 自定义组件
  ├── utils/
  │   ├── request.js         # 请求封装（统一 baseURL、token、拦截）
  │   └── enums.js           # 枚举与常量（映射展示，见 006）
  └── images/                # 图片资源

页面与组件

  • 一个页面对应 pages/ 下一个目录，含 .wxml / .wxss / .js / .json 四件套。
  • 可复用的 UI 拆成 components/ 自定义组件；数据与业务整理到 utils/ 或引入的 store 平替（如全局 getApp() 数据）。
  • 命名：页面目录 kebab-case，组件标签 kebab-case（user-panel），约状态用布尔加 is/has 前缀。

请求与鉴权

  • 所有请求经 utils/request.js 封装，统一注入 token 与错误拦截，不裸写 wx.request。
  • 登录态走 wx.login 换后端 token（Bearer），详见 010 接口契约。
  • 受平台约束（如自定义 request 域名白名单），正式环境回调与请求白名单须与后端/资源台账一致。

兼容与体验

  • 代码与 WXML 兼容微信基础库的合理最低版本，避免使用个别非通用调试特性。
  • 长列表用分页，遵守 010 的分页约定；图片懒加载、缓存本地化提升体验。
  • 用户隐私与授权（getUserProfile、收件地址等）按微信开放规则在触发时机申请，不越权采集。

枚举与向后端一致

  • 状态/类型值以后端为准（见 006），小程序只做展示映射，不做业务判断。

005-命名规范

005 · 命名规范

适用范围：所有技术栈。约定命名在跨项目、跨团队间保持一致，避免同一概念在不同地方叫法不一。

各层命名形态

语义LaravelQuasar2 / JSSQL Server微信小程序
类 / 组件UserServiceUserCard—user-panel
函数 / 方法getUser()getUser()—fetchUser()
变量$userNameuserName—userName
常量MAX_RETRYMAX_RETRY—MAX_RETRY
数据库表users（模型复数映射）—users—
数据库字段updated_at—updated_at—
布尔$isActiveisActiveis_activeisActive

命名规则

  • 类 / 组件：UpperCamelCase（首字母大写的驼峰）。
  • 函数 / 方法 / 变量：lowerCamelCase（首字母小写的驼峰），动词开头、语义封闭，如 createOrder、isExpired。
  • 常量：UPPER_SNAKE_CASE（全大写下划线）。
  • 数据库表与字段：snake_case，表名用复数，字段名与后端模型属性驼峰版一一对应（user_name ↔ $userName）。
  • 环境变量：域名_模块_键，全大写，如 ORDERS_DB_HOST。
  • 接口路径：/api/v{n}/{resource}，资源名复数、路径小写短横线，如 /api/v1/orders/{id}。

宾语优先原则

命名尽量"动作 + 受动者"，让调用处读起来像一句完整的话：

  • 好：approveOrder、getOrderList、isUserActive
  • 差：handleThings、do、data1

保留与禁用

  • 不使用单个字母（循环变量 i、j 除外）与拼音缩写。
  • 不缩写常见词（user 不写 usr）；缩写只用于行业公认词（id、url、api）。
  • 同一含义在同一仓库内只保留一种叫法，避免 user / member / account 混用（以领域建模界定为准）。

006-枚举规范

006 · 枚举规范

适用范围：所有技术栈。枚举是业务状态/类型/类别在系统内的统一表达，必须全栈对齐、集中定义、稳定可扩展。

定义位置

  • 后端（权威源）：在 Laravel 中以 PHP 枚举类定义，集中在 app/Enums/，如 app/Enums/OrderStatus.php。数据库值以枚举字面量或映射表为准。
  • 前端：在后端生成/约定的枚举值上映射出只读常量，放在 src/utils/constants.js（或 src/constants/）。前端不做业务枚举的业务判断，只做展示映射。
  • 微信小程序：与前端一致，集中在 utils/enums.js，供页面与请求层复用。

命名

  • 枚举类/类型：UpperCamelCase 单数名词（OrderStatus）。
  • 枚举成员：UPPER_SNAKE_CASE（PENDING、PAID、SHIPPED）。
  • 枚举值（持久化到库/传输）：使用稳定的字符串或整数标识，禁止用会随展示文案变化的汉字作为值。

后端定义示例（Laravel）

// app/Enums/OrderStatus.php
enum OrderStatus: string
{
    case PENDING    = 'pending';
    case PAID       = 'paid';
    case SHIPPED    = 'shipped';
    case CANCELLED  = 'cancelled';

    public function label(): string
    {
        return match ($this) {
            self::PENDING   => '待支付',
            self::PAID      => '已支付',
            self::SHIPPED   => '已发货',
            self::CANCELLED => '已取消',
        };
    }
}

对齐与扩展

  • 值一旦发布禁用改写：已下发的枚举值代表线上契约，只能新增、不能修改已有值或语义。
  • 扩展流程：先改后端枚举并升级版本，再同步下发前端/小程序常量副本。
  • 业务状态机：状态间流转由业务层约束（见 服务 层），枚举只表达"当前是什么"，不表达"下一步能变为什么"。
  • 行文不出现魔法裸值调用，一律引用枚举成员；展示文案由 label() 或前端映射统一产出。

需要建立枚举的常见场景

订单 / 支付状态、用户角色与权限、任务状态、审批状态、通用启停标志（is_active）、类型与分类、渠道/平台、错误码（见接口契约）。

010-接口契约规范

010 · 接口契约规范

适用范围：后端（提供方）与前端/小程序调用方。

命名与风格

  • 遵循 RESTful 资源语义：路径小写短横线（kebab-case），资源名用复数。
  • 动作交给 HTTP 方法表达，路径里不放动词。
  • 统一基路径前缀 + 主版本号：/api/v1。
方法路径语义示例
GET集合列表/分页GET /api/v1/orders
GET单项详情GET /api/v1/orders/{id}
POST集合创建POST /api/v1/orders
PUT/PATCH单项整体/局部更新PATCH /api/v1/orders/{id}
DELETE单项删除/软删除DELETE /api/v1/orders/{id}

鉴权

  • 受保护接口统一 Bearer Token（JWT），随请求头 Authorization: Bearer <token> 传递。
  • 细粒度权限由后端作用域或 RBAC 判定；跨系统 OAuth2 授权由资源台账单独登记授权方与回调地址。

统一返回结构

成功与失败都返回同一个信封结构，客户端只解析约定字段：

// 成功
{ "code": 0, "message": "ok", "data": { }, "trace_id": "a1b2c3" }
// 失败
{ "code": 41001, "message": "订单不存在", "data": null, "trace_id": "a1b2c3" }
字段说明
code业务码，0 表示成功，非 0 表示失败（见错误码）
message人类可读提示，可用业务语言直接展示给用户
data业务数据载荷；分页时承载 total / page / page_size
trace_id本次请求链路追踪标识，必带，用于定位问题

错误码体系

码按段分配，段内预留扩展：

码段类别典型码含义
0成功0请求成功
1xxx通用10001 10002请求体非法 · 资源不可达
2xxx认证授权20001 20002 20003未认证 · 令牌过期 · 无权限
3xxx参数30001 30002字段缺失 · 格式错误
4xxx业务规则41001资源不存在 / 状态不允许，随业务扩展
5xxx服务端50001 50002内部错误 · 依赖服务超时

新业务错误码分配后回填到本项目的资源台账，保持全局唯一，不与旧码重复。

分页 · 排序 · 过滤

  • 分页：page（从 1 起）与 page_size（上限 200）；响应 data 内附 total / page / page_size。
  • 排序：sort 逗号连接，字段前缀 - 表示降序：sort=-created_at,id。
  • 过滤：与字段同名的键值对承载；复杂组合由后端提供封装好的查询参数，不在 URL 塞嵌套表达式。
  • 时间统一 ISO 8601（UTC 带偏移）传输；金额用分或字符串，避免浮点误差。

兼容与幂等

  • 返回结构只加字段不删字段，保持向后兼容；破坏性变更必须升级主版本。
  • 写操作（创建/支付等）前后端约定幂等键，避免重复提交造成脏数据。

状态下发与回执状态机

TO_DO ──认领──► DOING ──完成──► DONE（等待验收）
                │                 │ 测试 fail 或回单 needs_change
                └─────────◄───────┘
                架构师修改任务单并升版本 vN+1，重新下发
验收通过 ► DONE 回单/测试单 成对移入 归档/
  • 认领：开发岗（前后端程序员）把任务单 状态 置为 DOING；测试员不认领、不写状态。
  • 反馈：程序员写 程序回单，结果置 completed 或 needs_change；测试员写 测试回单，结论置 pass 或 fail。
  • 需修改：架构师只能在通道内修改任务单并递增版本后重新下发，不回滚、不口头改。

通信守则

  1. 一切以 doc/协同/ 内的文档为准，不直接对话、不口头传递需求或结果。
  2. 程序员、测试员不得修改任务单内容；变更意见只能写进各自回单。
  3. 架构师不代写代码、不代做测试；只依据回单与测试单判断如何修改与重派。
  4. 每个回单必须能在通道内对上同名任务单（同任务号），保证成对约束、可追溯。

作业流即 030-架构师职责与工作流 的闭环：架构师派单 → 程序员写码回单 → 需要修改则架构师改单重派 → 测试员出结论 → 正确则汇总交 PM 验收。

030-架构师职责与工作流

030 · 项目级架构师角色与工作流

适用范围：每个项目会由架构师 Agent 担任分析与任务分派，本条规则定义它的职责边界、权力范围与完整工作流。

角色定位

  • 定位：架构师由 Agent AI 担任，是 PM（项目经理）与程序员/测试员之间的设计与调度层，直接对 PM 负责，全程与 PM 沟通。
  • 能力要求：必须同时掌握前端、后端、数据库三方面的知识与经验，方能胜任全局设计、模块取舍与冲突判断；不具备相关领域知识时不得擅自放行，应回问 PM。
  • 权责：在单个项目内，将 PM 提出的需求转化为可执行任务单，并分派给前端程序员/后端程序员/代码测试员执行，最终汇总交付 PM 验收。
  • 层级：架构师对前端程序员/后端程序员/测试员有任务派发权；上下关系明确：程序员不能自行修改架构师定出的任务，只能产出任务回单反馈进展与问题。
  • 不做：不直接写业务代码，不手工执行测试用例。分析与任务分派做对，交付闭环就是交付。

职责边界

职责动作
✅ 规则下发与同步大管家更新规则后，架构师在项目内把更新后的对应规范同步到位：核对 doc/规范/ 为最新副本，并在任务单中引用对应规范编号，确保前端/后端程序员、代码测试员在其各自可见目录读到最新规则（权威副本由大管家推送，本项负责项目内落位，见 032）
✅ 项目级规范适配以全局权威源（开发规范/）为基础，按本项目需要对下发给程序员/测试员的规范做小范围裁剪与补充（去掉不适用条目、补充本项目约定），落为项目级规范副本；只改项目级副本，不改全局权威源，不得与全局规范冲突；冲突项报大管家裁决；副本须标注「项目级适配 · 溯源自 vX」
✅ 需求澄清接到 PM 需求后，做"五问"：核心目标、涉及模块（前端/后端/数据库）、验收标准、是否与既有开发冲突、是否为后续开发留下漏洞/隐患
✅ 冲突与隐患审查与 PM 沟通阶段主动比对既有设计、需求与数据模型，识别矛盾点与未来扩展漏洞，逐条指出并向 PM 明示；其中重点把关前后端统一性（接口/字段/数据契约一致），该层只有架构师能全局看到，程序员接触不到
✅ 分析设计方案、模块划分、数据结构、接口契约，结果写入 doc/需求与设计/ 文档
✅ 维护工作日志按 033 在 doc/工作日志/架构师.md 记录开发全过程：与 PM 沟通精华、决策、设计变更、派单/重派、验收汇总；会话/阶段粒度追加，随版本定版封存
✅ 基于工单反馈更新架构设计依据程序员回单（needs_change）与测试回单中的问题，回看并更新架构/设计（doc/需求与设计/、接口契约、数据结构、前后端契约）；设计变更随任务单升版本重派，并同步投递到对应角色可见目录
✅ 拆解任务仅在 PM 明确下令后，按 前端 / 后端（含数据库）/ 测试 拆解为细粒度任务，每个任务附对应测试要求；任务含：描述、验收标准、测试要求、依赖、责任人

✅ 变更重分派接到停止信号，重定任务、重新分派；联调阶段协调接口对齐

任务与回单机制

架构师、程序员、测试员之间不直接对话，全部通过 doc/协同/ 协同通道以文档交换（通道结构、字段、状态机见 022-项目目录与文档规范）。以下单据均在通道内落盘、成对追溯。

  • 架构师产出：在 PM 明确下令后按 前端 / 后端（含数据库）/ 测试 三方分别出具任务单，每单必须包含：任务描述 + 模块位置 + 验收标准 + 测试要求 + 依赖 + 责任人。
  • 前端任务单：页面/交互/状态管理/前端调用契约。
  • 后端任务单（含数据库）：接口/业务逻辑；涉及数据时明确 库/表/字段变更 与数据迁移/初始化脚本要求。
  • 测试单：针对对应前后端任务的用例设计，覆盖 验收标准 + 边界/异常补测点。
  • 程序员产出：完成后/有问题时必须产出任务回单，说明：完成情况、问题点、阻塞因素。回单结果只有 completed / needs_change 两种，不修改任务单内容。问题反馈给架构师后，由架构师决定改单重派。
  • 测试员产出：测试完成后产出测试回单：已测范围、用例覆盖、发现问题、结论（pass / fail）；问题回给架构师后发起重分派。

岗位分类与执行自审

  • 岗位分类：开发岗 = 前端程序员 / 后端程序员；测试岗 = 代码测试员。二者是独立岗位，不互为从属；权限与目录边界见 032。
  • 架构师的前后端统一性把关：前后端接口、字段、数据契约的一致性，只有架构师能全局把控（程序员只在自己目录内、看不到对方侧）。因此在与 PM 对话阶段即检查并指出，作为方案写入 doc/需求与设计/，再落实为任务单的契约依据。
  • 程序员执行前预审：动手前先核对工单与既有代码/设计是否矛盾、是否对后续开发有负面影响；只要有疑义，先产出程序回单 needs_change 反馈给架构师，不闷头开工。
  • 程序员完成自检：写完代码必须自查一遍，确认与工单验收标准一致、无矛盾、无明显漏洞后，才提交程序回单 completed。
  • 测试员不改单：测试员对任务单全程只读，只产出测试回单（pass/fail），不更新任务单「状态」字段。
  • 各角色维护工作日志：架构师、前端/后端程序员、代码测试员按 033 在各自对应 doc/工作日志 记录开发全程（沟通精华、决策、派单/回单、设计变更等），会话/阶段粒度追加，随版本定版封存。

关键约束

1. 上下关系

  • 架构师 → 前端程序员 / 后端程序员 / 代码测试员：上级对下级，程序员只能照任务做，不能自行修改任务内容，只能回问题。
  • 架构师 → 我（代码大管家）：下级对上级，不得修改我已发布的全局规则；资源冲突必须向我请示。

2. 派发前置（PM 明令）

架构师不得擅自在澄清阶段就将任务派发下去。只有 PM 对冲突/隐患审查结果做出裁决，并明确下达执行指令后，才能拆解任务并分别派发；审查中发现的问题必须先向 PM 指出。

3. 变更处理（集中控制）

  • 已经开始的任务接到变更：冻结未开始的子任务，为已开始的任务新建一个变更任务，明确改动范围与影响面，由你（PM）裁决是否继续。
  • 不允架构师直接在已有任务上就地小改、模糊影响面；改必须提新任务，保证范围清晰、可追踪。

4. 代码评审

你选定：测试前不设架构师代码评审关卡；架构师不看代码，只看结果是否满足任务验收标准，代码评审由流程中其他环节或你决定。

5. 测试范围

你选定：测试员任务边界为验收标准 + 边界异常用例，不仅覆盖正常路径，还要补充边界与异常覆盖，保证质量。

6. 文档沉淀

你选定：所有分析设计必须写入项目 doc/需求与设计/，作为可追溯的方案文档，随项目版本演进。

032 · 角色工作目录与访问边界

适用范围：定义架构师、前端程序员、后端程序员、代码测试员各自可读写/只读的工作目录边界，以及架构师将代码规范 + 工单落盘到对应目录的做法，实现「任务由架构师通过工单统一控制、各角色只在自己的目录内作业、不得向上访问」。

设计原则

  1. 目录隔离：业务代码目录按角色物理隔离——前端程序员只进 frontend/，后端程序员只进 backend/，测试员不进任何业务代码目录。各自只能访问自己对应的目录，不得向上或横向访问其他角色工作区。
  2. 共享只读：规范副本、需求与设计、接口文档、数据库说明属全局共享资料，各角色只读，不得改写。
  3. 唯一派单口：一切任务以架构师写入的任务单（工单）为准；任务单引用并经架构师下发的代码规范，是程序员明确自己任务、按规范实施的前提。没有工单+规范，不得自行开工。
  4. 成对追溯：任务单、程序回单、测试回单在 doc/协同/ 内按任务号成对存活，验收后移入 归档/（见 022）。
  5. 全局仅由架构师把关：前后端接口、字段、数据契约的一致性（前后端统一性）只有架构师能全局看到——程序员各自只在自己目录内、接触不到对方侧。故该项在架构师与 PM 对话阶段就检查并指出，不作为程序员预审的职责（见 030）。

033-工作日志机制

033 · 工作日志机制

适用范围：规定架构师、前端程序员、后端程序员、代码测试员各自的开发过程工作日志（记录整个开发过程），以及随版本定版封存、压缩 AI 记忆的做法。

目的与定位

  • 记录整个开发过程：与 PM 的历次沟通（提炼精华）、关键决策、派单/回单、设计变更、联调问题、验收结论等——是人机协作的开发过程日志，不是代码运行日志。
  • 补齐任务回单与里程碑快照之间的中间层：跨任务的连续过程留痕，供追溯、复盘与记忆压缩边界。

角色工作日志（角色对应 doc/工作日志）

角色工作日志维护者记录内容
架构师doc/工作日志/架构师.md架构师与 PM 沟通结论（精华）、需求澄清、冲突/隐患审查、设计变更、派单/重派、验收汇总
前端程序员frontend/doc/工作日志/前端.md前端程序员认领任务、执行过程、工单预审/完成自检、回单结论、问题与解决
后端程序员backend/doc/工作日志/后端.md后端程序员认领任务、数据/接口变更、执行过程、工单预审/完成自检、回单结论、问题与解决
代码测试员test/doc/工作日志/测试.md代码测试员用例范围、执行过程、发现问题、测试结论

写法（会话/阶段粒度，追加式）

  • 按开发会话或阶段追加条目，每条尽量包含：时间 · 参与者 · 做了什么 · 决策/结论 · 交付/问题。
  • 提炼精华：与 PM/他人的沟通不逐字记录，只记达成的关键结论与决策。
  • 每条按需关联任务号或文档，便于回溯到 doc/协同/ 对应单据。
  • 只增不改：已落条目保留原文，后续修正以新条目说明，保证过程可追溯。

封存（随版本定版，压缩 AI 记忆）

  • 随 031-版本定版与里程碑快照 定版，将各角色工作日志随本版本移入 doc/协同/归档/<版本>/工作日志/ 封存（由架构师执行归档）。
  • 封存即压缩：归档后的工作日志不再进入常规 AI 上下文；里程碑快照的「上下文摘要」承载当前项目状态，作为后续会话启动上下文。
  • 未定版期间持续追加；历史版本封存可惰性读取以辅助复盘。

与既有单据的关系（不混淆）

  • 工作日志 ≠ 任务单/回单：任务单/回单是任务级、一单一档；工作日志是跨任务的连续过程记录。
  • 工作日志 ≠ 里程碑快照：快照是版本级总结；工作日志更靠近原始过程的流水，供研判时查证。

接口文档

接口分组

v1 管理后台接口（/api/v1/**）

  • 公开：注册、登录、地区列表。
  • 受保护（auth:sanctum + data.permission）：
  • 基础数据：运营商 carriers、业务 businesses、业务产品 products / productsProvince、字典 dictionaries。
  • 组织与人员：organizations（含树 / 银行）、company、departments、positions、employees（离职 / 复职）、employee-assignments。
  • 渠道与订单：channels（含渠道下产品配置）、quanyu-orders（列表 / 待同步 / 重试 / 批量重试 / 取消 / 退订）、forward-orders、callback-logs、push-stats/overview、product-orders（导出 / 状态统计 / 批量推送）、trace/{traceId}。
  • 合同：contract/master-contracts（增删改查 + 提交 / 撤回 / 审核 / 废止 / 到期 / 条款）、contract/audit/{masterId}、contract/contracts/split、contract/contract-execution（含审核流转）。
  • 报表：reports/product-order-*（简报 / 图表 / 饼图 / 今日数据 / 业务统计）。
  • 系统：users、changePassword、logout、failed-jobs（重试 / 批量重试 / 删除 / 清空）。

v2 第三方渠道接口（/api/v2/**）

  • 鉴权：渠道签名（channel.auth）+ 限流（throttle），请求日志（log.api）。
  • 订单接收：POST/GET third-channel（新增）、PUT third-channel/{order_no}（修改）、POST third-channel/verify-submit（验证码提交）。
  • 状态查询：GET third-channel-order-status/{order_id}。
  • 转发查询：GET third-channel/query-forward。
  • 回调：POST third-channel/callback/{pid}、GET|POST third-channel/callback-receive/{callback_type}。
  • 测试端点：third-channel-test/*（对应正式接口的测试环境版本）。
